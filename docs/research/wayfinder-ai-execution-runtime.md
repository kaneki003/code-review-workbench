# Reusing a local command runtime for AI investigations

Research checked 15 October 2026 for [Choose AI runtime and investigation contracts](https://github.com/kaneki003/code-review-workbench/issues/10). This is planning evidence, not implementation or a verified security boundary. No installation, authentication, inference or sandbox workload was run. The owner has selected AI SDK Core with direct Gemini/OpenAI keys and one provider at a time.

## Recommendation

Reuse **Microsoft MXC**, provisionally pinning `@microsoft/mxc-sdk` **1.0.0**, beneath a small Workbench-owned execution interface. Keep AI SDK's provider loop, private history and human permissions in Workbench. MXC handles OS containment and process ownership; it does not choose the AI provider. Its first stable V1 SDK release was published on 7 October 2026. This is a concrete dependency to validate, not a claim that packaging or the three-platform boundary already works. [Release](https://github.com/microsoft/mxc/releases/tag/v1.0.0), [versioned API](https://github.com/microsoft/mxc/blob/main/docs/api-reference/node/v1/README.md).

**The tractable first configuration is offline AI-run commands.** Online model requests and explicit GitHub product actions still run in the extension host. Adding online shell execution while preserving human-only publication needs another containment decision; a general network approval or a shell-name blacklist does not provide that separation.

For the initial product matrix, retain Windows x64, Linux x64 and macOS arm64. Unsupported command containment must disable that command with a useful reason while leaving supported review features available; never silently retry outside the sandbox. This requires owner acceptance because it narrows where automatic checks work.

## How Workbench would call it

Import from `@microsoft/mxc-sdk/v1`; its package root exposes no public API. `spawn(ContainerRequest)` returns separate live input/output/error streams, `wait()`, `kill()`, warnings and disposal. `spawnWithPty` also exists, but backend support differs. Prefer owned pipes for noninteractive checks, displayed in an identifiable VS Code `Pseudoterminal`; this display does not require the child to have an interactive PTY. Do not inject into an existing terminal. Read output before waiting and retain a bounded transcript independently of terminal lifetime. [Launch API](https://github.com/microsoft/mxc/blob/main/docs/api-reference/node/v1/api.md), [VS Code terminal API](https://code.visualstudio.com/api/references/vscode-api#Pseudoterminal).

Expose structured `executable`, `argv`, `cwd` and operation identity to application code. **MXC itself accepts a command string**, so executable/argument separation is an adapter responsibility. A fixed packaged launcher receiving structured arguments over stdin is one possible design; blindly joining model arguments into a shell string is not. This needs implementation validation rather than an invented shell parser. [Request fields](https://github.com/microsoft/mxc/blob/main/docs/api-reference/node/v1/types.md).

Workbench must own task-scoped grants: show the command and affected paths; check the current grant immediately before each dispatch; stop related active commands when revoked; launch subsequent commands with a fresh policy. No documented universal API retroactively removes filesystem rights from an already-running MXC process. Source-changing commands follow the same grant policy; a writable project grant permits writes by tests/scripts too. Revocation cannot undo completed changes. These are proposed application rules, not MXC features.

## Credential and publication boundary

Use narrow read/write project and per-run scratch paths, read-only necessary tool installations, a separate clean home, and explicit exclusions for private state and credential locations. Keep provider/GitHub credentials in host-owned storage; never put them in command arguments, environment or results. Supply a constructed environment rather than `process.env`: do not inherit API tokens, agent sockets, editor IPC, credential-helper settings, startup files, runtime preload variables or arbitrary user proxy variables. Workspace dotfiles and scripts remain untrusted inputs. A project read grant can expose secrets stored in that project; MXC is not a secret detector.

The Linux backend clears host environment and gives an isolated network stack. Its default home can be the working directory, so explicitly select a clean home. Offline Linux processes can use their own loopback for tests, but cannot reach existing host services. [Linux environment/network behavior](https://github.com/microsoft/mxc/blob/main/docs/backends/bwrap/bubblewrap-backend.md).

On macOS, keep Keychain/GUI access disabled. Deny network egress, ingress and host loopback. A writable path can also permit connecting to **Unix sockets underneath it**; never grant the whole home or shared temporary tree. Explicitly exclude sensitive sockets and validate host/editor IPC routes. With all IP networking denied, tests that bind/connect localhost can fail on macOS, including tests that would run inside Linux's private loopback. [Seatbelt behavior](https://github.com/microsoft/mxc/blob/main/docs/backends/seatbelt/seatbelt-backend.md).

Windows can select BaseContainer or AppContainer fallback tiers. The raw schema permits a fallback that temporarily changes host file ACLs; it defaults to allowed. The public V1 request does not expose that fallback switch. Probe the **actual request**, require the intended tier/capabilities, and resolve any need to forbid ACL mutation before enabling that Windows configuration; do not assume the high-level SDK already forbids it. [Fallback policy](https://github.com/microsoft/mxc/blob/main/docs/schema.md#fallback-policy), [V1 request/config fields](https://github.com/microsoft/mxc/blob/main/docs/api-reference/node/v1/types.md).

Offline execution plus inaccessible credentials/host control channels is the proposed publication boundary. It is not a proof against every malicious project or later human execution of edited files. A blocked command must report that its check was not completed; do not run it on the host automatically. Windows named-pipe/editor brokers, Unix sockets in allowed directories, symlinks, external tool configuration and helper access need adversarial acceptance fixtures.

## Why online command approval is additional work

MXC supplies containment, **not a destination-filtering HTTP proxy**. Its numeric egress rules are not domain policies. macOS can confine egress to a caller-managed proxy port, but cannot enforce arbitrary hostname/IP lists itself. Linux online modes add slirp4netns, util-linux and namespace-local firewall prerequisites. For Windows, the schema distinguishes an identified proxy peer from a weaker identity-less loopback proxy: the latter opens other host-loopback routes. A normal Node loopback proxy is therefore not automatically equivalent to strict cross-platform confinement. [Networking contract](https://github.com/microsoft/mxc/blob/main/docs/schema.md#directional-networking-supported-contracts).

Dependency downloads and external-service checks consequently cannot run in the proposed first command lane. Narrow online grants require a maintained proxy/credential boundary and platform verification before they can preserve the publication promise. Blocking `gh`, `git push`, `curl` or other executable names cannot enforce it: another program can make the same request.

## Stop, packaging and remaining evidence

The native runtime owns process lifecycle. Node's V1 wrapper forwards kill, waits for native settlement and exposes cleanup failures. The public process result does not enumerate every descendant; this research does not establish a universal guarantee about deliberately detached descendants or host crashes. Workbench should retain text/output, stop new tool dispatch immediately and show “stopping” until settlement; on failure/restart keep an honest unknown state. Killing a plain Node child is insufficient: Node documents that Linux grandchildren can survive their parent. [Native SDK](https://github.com/microsoft/mxc/blob/main/src/mxc-sdk/README.md), [V1 process implementation](https://github.com/microsoft/mxc/blob/v1.0.0/sdk/node/src/v1/container-process.ts), [Node child-process limits](https://nodejs.org/api/child_process.html#subprocesskillsignal).

MXC's Node package includes native runtime assets and depends on native `koffi` and `node-pty`. Preserve runtime assets through pnpm/esbuild/vsce; the existing CommonJS host must load the ESM package deliberately. Test the **installed VSIX**, actual Electron host and each advertised architecture; do not infer compatibility from developer Node alone. The MIT license requires retaining its notice and does not require publishing Workbench source. [Package manifest](https://github.com/microsoft/mxc/blob/main/sdk/node/package.json), [distribution overview](https://github.com/microsoft/mxc#how-do-i-use-mxc), [license](https://github.com/microsoft/mxc/blob/main/LICENSE.md).

Release gates: package loading; safe toolchain discovery; credential/IPC/network denial including IPv6; inside/outside/symlink path rules; source writes under ordinary grants; normal user terminals untouched; revocation during spawn; descendants and changed process groups; retained output on Stop; extension-host crash/restart uncertainty; policy/probe rejection without unsandboxed fallback. No such fixtures were executed in this research.
