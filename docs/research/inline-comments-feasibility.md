# Inline discussion and private AI suggestions: host feasibility

Checked 12 October 2026 against official documentation, the stable VS Code 1.141.0 declaration/source, and Microsoft's comment sample. VS Code 1.141 was released on 7 October 2026. This is a source review, not a native extension test. It revises the concepts without selecting a final direction. [Stable release](https://code.visualstudio.com/updates/v1_141).

## What the ordinary editor can support

Native comment threads can anchor to a document/range, expand and collapse, display Markdown, author information, labels and timestamps, support replies and contributed actions, and show resolved/unresolved state. A thread's icon is anchored to the last line of its range. A separate controller can hold private AI suggestions, with `canReply = false` and controller-specific actions. Those threads appear in the host Comments Panel as well as matching editors; removing the extension's dedicated Discussion view does not remove this native host view. [Comment API](https://code.visualstudio.com/api/references/vscode-api#CommentThread), accessed 12 October 2026.

The ordinary diff uses two document URIs. Anchoring to the reviewed revision or original revision determines which source has the thread; this is separate from the visual placement of its marker. Stable decoration options offer `gutterIconPath`, before/after text attachments, hover content and overview-ruler coloring. They do not offer a click callback, arbitrary editor HTML, a right-edge marker lane, a custom comment-thread glyph, or controller-specific gutter-side placement. The declaration also has no native comment-input typing event. These are limits of the stable public contract, rather than a claim that internal VS Code code cannot do them. [Stable declaration](https://github.com/microsoft/vscode/blob/1.141.0/src/vscode-dts/vscode.d.ts), accessed 12 October 2026.

## Requested behavior and its practical boundary

| Request | Feasibility in ordinary native code/diff | Design implication |
|---|---|---|
| Click a discussion marker to expand the anchored thread | Supported through native comment threads | Preserve the familiar discussion interaction; let VS Code draw its marker and widget. |
| Render private AI suggestions at their code location | Supported using a distinct native comment controller | Label the controller and card **Private AI suggestion**; use a distinct author avatar, text labels and actions. A controller is a UI owner, not a privacy or publishing mechanism. |
| Put GitHub and AI markers on opposite visual sides of the same code editor | No stable placement contract | A right-edge AI marker in the browser is an illustration, not a verified native capability. A left/right split diff represents old/new code, not public/private ownership. Do not relocate a finding onto the old source merely to achieve symmetry. |
| Compare icon-only disclosure with a GitHub-style collapsed horizontal comment row | Native collapsed thread is supported; arbitrary collapsed row composition is not exposed | Show both illustrations with a host limitation note. A short clickable CodeLens above an anchor could approximate a text-row entry point, but does not reproduce GitHub's below-line strip and can add vertical density. Verify it in a small host check before relying on it. |
| Show category, impact, freshness and evidence in an expanded suggestion | Plain labels/Markdown and actions are supported; arbitrary badge/card HTML is not | Prefer readable text such as **Private · Security · Major · Source outdated**. Rich pill styling in a browser mock is simulated unless mapped to supported native text. Keep evidence links and explicit adoption actions. |
| Keep the assistant free for open-ended questions | Feasible interaction arrangement | Move code-anchored findings/discussion out of the assistant. Cross-file or file-level findings still need an accessible locator and file anchor so they are not lost outside visible changed lines. |
| Remove the separate Discussion panel | Feasible for an extension-owned view | Retain thread/file counts and next/previous navigation in review navigation. Native comment threads will still be listed in VS Code's optional Comments Panel. |

Microsoft's official sample shows contributed comment/reply/draft/edit actions and `contextValue` scoping. Use the controller context on every action so **Comment / Start a review / Add review comment** cannot accidentally appear on a read-only private suggestion. This confirms action contribution, not GitHub delivery, draft durability or custom styling. [Sample implementation](https://github.com/microsoft/vscode-extension-samples/blob/main/comment-sample/src/extension.ts), [sample menus](https://github.com/microsoft/vscode-extension-samples/blob/main/comment-sample/package.json), accessed 12 October 2026.

## Unfinished typing must not be mistaken for a pending GitHub review

The stable native comment action receives `CommentReply.text` when invoked. That is insufficient to promise autosaving every unfinished keystroke. Stable VS Code's widget explicitly has a confirmation path warning that collapsing can discard unsubmitted comments. Do not assume the host preserves raw input across collapse, navigation, extension reload or review exit. [Stable comment widget implementation](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/comments/browser/commentThreadZoneWidget.ts), accessed 12 October 2026.

GitHub Pull Requests currently declares `commentReveal`, `commentsDraftState`, `activeComment` and other proposed APIs. Its behavior therefore does not establish the capabilities available to a new stable-only extension. `commentReveal` supplies explicit thread reveal/focus/hide; `commentsDraftState` marks an existing comment as Draft/Published, rather than offering a typing-autosave event. [GitHub extension manifest](https://github.com/microsoft/vscode-pull-request-github/blob/main/package.json), [comment reveal proposal](https://github.com/microsoft/vscode/blob/main/src/vscode-dts/vscode.proposed.commentReveal.d.ts), [draft state proposal](https://github.com/microsoft/vscode/blob/main/src/vscode-dts/vscode.proposed.commentsDraftState.d.ts), accessed 12 October 2026.

**Design judgment:** Preserve the user's requested automatic-draft behavior. If stable native input cannot satisfy it, keep native inline thread reading and open a compact extension-owned composer beside the ordinary editor for writing. The owned input can autosave unfinished text with no **Save local draft** action. Its clear destination stays **Unsent draft** until the reviewer chooses **Comment** or **Start a review**; with a pending review, show **Add review comment**. Choosing those actions is a GitHub transition, not merely a save. The finish-review surface can then offer summary plus **Comment / Approve / Request changes**. This is an interface fallback to validate, not an architecture decision.

## Keyboard and focus

Native comments have host navigation and an Accessible View. Native diff provides F7/Shift+F7 change navigation and an Accessible Diff Viewer. The stable comment controller implementation locates previous/next threads and can focus them; explicit extension-level thread focus is also an area where the GitHub extension uses the reveal proposal. [Accessibility guidance](https://code.visualstudio.com/docs/configure/accessibility/accessibility), [stable comment navigation implementation](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/comments/browser/commentsController.ts), accessed 12 October 2026.

**Design judgment:** Every discussion/finding must be reachable through a named command and review navigation, not only an icon or hover. After inspecting evidence, return to the original file/range. When a thread collapses, restore code focus; test this rather than promising exact focus control from the browser. Distinguish public/private and category/impact in text, not only marker color or position. Check co-located threads, high contrast, keyboard-only navigation, split/unified diff, and moving between original/modified editors.

## Recommended bounded host check

Keep the native editor. Before finalizing exact marker visuals, register two mocked controllers on one small native diff, including a GitHub discussion and a private AI suggestion on the same line. Verify native collapse/expand, multiple-thread selection, original/modified anchors, labels/actions, keyboard focus, themes and narrow width. Add one optional CodeLens row and compare its density with icon-only disclosure. Separately verify unfinished input through collapse/navigation/reload; if it is lost, exercise the owned autosaving composer fallback. No GitHub publishing, AI retrieval or repository architecture is needed for this check.

A custom editor is officially a webview with a separately implemented UI. It could reproduce the exact strips and right-edge controls, but would replace the ordinary editor experience inside that surface. **Design judgment:** that cost conflicts with code centrality and proportional scope for a solo builder, so it is not the recommended response to this marker constraint. [Custom Editor API](https://code.visualstudio.com/api/extension-guides/custom-editors), accessed 12 October 2026.
