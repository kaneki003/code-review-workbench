# Stable desktop VS Code host capabilities

Checked 15 October 2026 for [Establish stable VS Code host and runtime capabilities](https://github.com/kaneki003/code-review-workbench/issues/2). Fact-finding only; no native host experiment or framework/architecture selection has been performed. The approved PRD, reconciled design contract and current user answers govern: ordinary source/diff tabs, exact unfinished-text retention, right Context / Chat companion, stable desktop APIs, and owner review of any composer compromise.

## Main finding

The refreshed stable target is **VS Code 1.142.0, released 14 October 2026**, rather than the 1.141 baseline in the earlier research. Windows, macOS and Linux distributions are listed by the release. This is a research baseline, not a decision to require that version. [Official release](https://code.visualstudio.com/updates/v1_142), [release archive](https://code.visualstudio.com/updates/archive).

**The approved owned inline autosaving writer remains a stable-API gap.** The stable declaration exposes a native comment reply's text as a command argument when an action runs, but exposes no native reply-input change event/value API or arbitrary extension-owned HTML zone beneath a source line. A webview is a separate view/panel/custom editor, not an insertion into an ordinary text editor. This is a conclusion from the public contract, not a native runtime test. Therefore native inline comments cannot currently substantiate exact unfinished-text autosave. Moving writing to an owned surface changes the approved inline composer and needs the owner's decision; do not silently move it into Context / Chat. [Pinned stable declarations, comments](https://github.com/microsoft/vscode/blob/1.142.0/src/vscode-dts/vscode.d.ts#L16318-L16626), [webview guide](https://code.visualstudio.com/api/extension-guides/webview), [custom editor guide](https://code.visualstudio.com/api/extension-guides/custom-editors).

## Feasibility

| Requirement | Stable capability / boundary | Status |
| --- | --- | --- |
| Ordinary reviewed source and diff tabs | Read-only URI content providers and `vscode.diff`; revision identity must be encoded and supplied by the extension | Supported mechanism; anchor/navigation behavior needs host checks |
| Current editable working files | Ordinary `file:` documents and editor APIs | Supported; immutable review identity must stay distinct |
| Navigation and movable companion | Native Tree Views/Quick Picks; webview views for owned content; view containers can be contributed to primary/secondary sidebar and Panel | Supported; fixed right geometry cannot be guaranteed |
| Native inline discussion/private suggestions | Comment controllers, range/file association, Markdown/text labels, actions, collapse/state and reply control | Supported reading; styling and exact focus constrained |
| Exact unfinished native comment text retained automatically | No public typing observer in stable comment API | Unsupported contract; blocks approved writer promise |
| Owned inline input in ordinary source/diff | No public arbitrary HTML/editor-zone insertion API | Unsupported contract |
| Separate owned autosaving input | Webview messages or native InputBox `onDidChangeValue` can expose typing | Mechanically feasible; changed product treatment requires approval |
| Durable state/credentials | Extension storage locations/Mementos and encrypted SecretStorage | Available; no promised transaction/crash-durability contract |
| Check output and Stop | Task lifecycle/terminate; terminal shell integration output events; own pseudoterminal/process alternatives | Available with limitations; cancellation must be verified |

## Editors, views and comments

The virtual-document guide explicitly demonstrates a read-only content provider opened in the ordinary editor and compared with `vscode.diff`. **Inference:** a URI carrying repository, commit and path can name immutable inspected content, provided the provider never substitutes newer content for that URI. Working files must use their separate editable document identity. Language features on custom schemes are provider-dependent; native presentation does not prove definition/reference support for historical content. [Virtual documents](https://code.visualstudio.com/api/extension-guides/virtual-documents).

Tree Views support hierarchical data, selection/reveal and item actions; Quick Picks suit repository/PR selection. Owned webview views suit the richer companion. `secondarySidebar` containers became available in 1.106; the current UX guide confirms users can move views/containers between sidebars and Panel. The documentation reference lags that release note, so use the explicit release example. **Inference:** the design can establish a default companion location, not permanent right-side geometry or sidebar width. [Tree View guide](https://code.visualstudio.com/api/extension-guides/tree-view), [Quick Pick guidance](https://code.visualstudio.com/api/ux-guidelines/quick-picks), [1.106 extension authoring](https://code.visualstudio.com/updates/v1_106#_view-containers-in-secondary-side-bar), [movable views](https://code.visualstudio.com/api/ux-guidelines/views).

Native threads provide range/file association, comments/Markdown, authors, labels, reply control, collapse and resolved state; create/remove affects matching editors and the native Comments Panel. The stable signature creates with a range, while the thread property supports `undefined` for file association: verify the creation/update sequence in-host. Thread ownership distinguishes actions, not privacy. The official sample demonstrates controller-scoped actions, including draft/edit/reply workflows; it does not establish autosave or GitHub delivery. Same-line controllers, old-side anchors and exact keyboard behavior remain experiments. [Stable comment contracts](https://github.com/microsoft/vscode/blob/1.142.0/src/vscode-dts/vscode.d.ts#L16318-L16626), [sample implementation](https://github.com/microsoft/vscode-extension-samples/blob/main/comment-sample/src/extension.ts), [sample menus](https://github.com/microsoft/vscode-extension-samples/blob/main/comment-sample/package.json).

There is no stable thread `reveal`/`hide`/focus method or custom thread glyph/side contract. Decorations/CodeLens can add supported text, hover and command entry points, but do not expose an owned inline input. Internal comment-editor URI/text models are not a documented extension mapping to a thread and must not become an autosave dependency. GitHub Pull Requests 0.170.0 declares `activeComment`, `commentReveal`, `commentsDraftState` and additional proposed APIs. Its UX is not evidence that those APIs are available to this stable-only extension; proposals are explicitly unstable and unsuitable for normal Marketplace publication. [Stable API](https://code.visualstudio.com/api/references/vscode-api), [GitHub extension manifest](https://github.com/microsoft/vscode-pull-request-github/blob/main/package.json), [proposed API policy](https://code.visualstudio.com/api/advanced-topics/using-proposed-api).

## Runtime, placement and packaging

Desktop local and remote extension hosts use Node.js through the manifest's `main` entry; the browser host is a WebWorker through `browser` and lacks Node APIs. `extensionKind` selects preference: `workspace` places execution with the repository/tools, while `ui` runs locally and cannot directly use remote files/processes. Workspace extensions can still contribute views. **Implication:** desktop local support does not establish WSL/SSH/container support; decide and test remote behavior explicitly. Never interpret a remote URI as a local OS path. [Extension hosts](https://code.visualstudio.com/api/advanced-topics/extension-host), [remote architecture](https://code.visualstudio.com/api/advanced-topics/remote-extensions#architecture-and-extension-kinds).

Pinned 1.142.0 source targets **Electron 43.7.7**, whose official release lists **Node 24.21.0**. This establishes the desktop dependency baseline by source inference; `process.versions` inside the actual extension host has not been measured, and remote runtime parity has not been checked. Do not infer host Node from the developer's shell Node or a provider SDK's package engine. [VS Code runtime pin](https://github.com/microsoft/vscode/blob/1.142.0/.npmrc), [Electron 43.7.7](https://releases.electronjs.org/release/v43.7.7).

`engines.vscode` declares the minimum supported API version; match type definitions and tests to that floor. VSIX can be platform-independent when dependencies permit; native modules/binaries introduce OS/CPU packaging and ABI compatibility work. **Planning implication:** compare pure-JavaScript/WASM dependencies against native bindings before selecting persistence or subprocess helpers. Native dependency validation must cover the actual packaged extension, not only shell tests. [Manifest](https://code.visualstudio.com/api/references/extension-manifest), [platform-specific VSIX guidance](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#platformspecific-extensions), [remote native-module guidance](https://code.visualstudio.com/api/advanced-topics/remote-extensions#native-nodejs-modules).

## State, secrets and webview boundaries

The official storage guidance distinguishes workspace/global key-value state from workspace/global storage URIs; use supplied locations rather than guessed VS Code paths. Mementos are plaintext; SecretStorage encrypts credentials, stores them on the client even for remote extensions, and is available from either host. Settings Sync is opt-in for selected global keys, not an automatic private-review backup. These APIs do not document a multi-record transaction or power-loss durability guarantee. **Inference:** durable draft acknowledgments, serialization, recovery and any cross-window coordination belong to the application/storage choice. [Extension storage](https://code.visualstudio.com/api/extension-capabilities/common-capabilities#data-storage), [remote storage and secrets](https://code.visualstudio.com/api/advanced-topics/remote-extensions#persisting-extension-data-or-state).

Electron documents platform differences: Linux `basic_text` can use a hardcoded password if no secret store is available. Therefore avoid an unconditional claim that SecretStorage supplies OS-keychain-strength protection on every Linux setup; verify supported keyring conditions and failure handling. [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage).

Webviews communicate by messages; their DOM can be destroyed when hidden. `getState`/`setState` preserve JSON UI state across hiding, but state ends with panel disposal; serializers restore registered panels after restart. `retainContextWhenHidden` costs memory and is not durable storage. Use an independently durable host record for drafts/history and a versioned message/acknowledgment boundary for owned inputs. Sanitize Markdown/HTML, restrict resource roots and use a restrictive CSP. Theme/font variables plus screen-reader/reduced-motion classes are available; framework choice does not remove accessibility work. [Webview lifecycle, security, theming and accessibility](https://code.visualstudio.com/api/extension-guides/webview).

Workspace Trust provides `isTrusted`, a grant event and `limited` manifest support; hiding a command is insufficient because it can still be invoked. **Planning implication:** code browsing/draft recovery and repository execution need separate capability handling. Test Restricted Mode explicitly. [Workspace Trust guide](https://code.visualstudio.com/api/extension-guides/workspace-trust).

## Terminal and cancellation constraints

Shell integration depends on supported shell/configuration and may be disabled or unavailable. `executeCommand` plus execution start/end events exposes command identity and exit status; `read()` captures raw output only after its first call, so attach immediately. `sendText` alone does not establish completion or exit code. An undefined shell exit code is ambiguous, including interruption. There is no stable general terminal-output tap or per-shell-execution cancel method; terminal disposal, sending Ctrl+C, TaskExecution termination, or owning the process each has different consequences. Do not equate a cancellation request with confirmed descendant termination. [Shell support/installation](https://code.visualstudio.com/docs/terminal/shell-integration), [stable terminal/task contracts](https://code.visualstudio.com/api/references/vscode-api#TerminalShellExecution), [Task Provider](https://code.visualstudio.com/api/extension-guides/task-provider).

**Design inference:** use dedicated workbench-owned execution/terminals, capture the inspected source/cwd and outcome, keep ordinary user terminals available, and preserve partial output through Stop/reload. Check process-tree termination on each supported OS before promising it. This research does not select tasks versus owned process/pseudoterminal execution.

## Small framework/toolchain shortlist

| Candidate | Fit and decision boundary |
| --- | --- |
| TypeScript host, bundled with esbuild; `tsc --noEmit` separately | Matches Microsoft's documented host bundling pattern; `vscode` stays external. Host runtime target remains a separately tested compatibility decision. [Bundling guide](https://code.visualstudio.com/api/working-with-extensions/bundling-extension) |
| Semantic HTML/CSS + small TypeScript webview | Smallest abstraction set; explicit DOM/state handling becomes maintenance work as Chat grows. This is an engineering tradeoff, not an API limitation. |
| React + themed semantic controls | Component/state model suits conversation and composer state; introduces a renderer/runtime dependency. Still requires VS Code theme tokens, CSP and host messages. [React model](https://react.dev/learn) |
| Lit + themed web components | Small reactive component layer based on web standards; custom elements/shadow DOM deserve focus, style and screen-reader checks. [Lit model](https://lit.dev/docs/) |

Do not use Microsoft's retired Webview UI Toolkit as the assumed maintained control foundation; its owner announced deprecation/archive for 6 January 2025. No alternate UI kit is required by the host. [Sunset notice](https://github.com/microsoft/vscode-webview-ui-toolkit/issues/561).

Official desktop integration tooling is `@vscode/test-cli` + `@vscode/test-electron` (Mocha), with pinned VS Code versions and separate trusted/untrusted runs. Pure domain/storage tests may run independently; browser component tests cannot prove native inline, focus or workspace lifecycle behavior. Package/install a VSIX in the desktop matrix before release. [Extension testing](https://code.visualstudio.com/api/working-with-extensions/testing-extension).

## Alternatives requiring a product decision

1. Preserve native inline **reading**, use an owned compact editor-side composer with exact source/thread header and automatic durable saves. Keep Context / Chat's role intact; exact placement must be reviewed. Most compatible with stable APIs, but changes approved inline writing.
2. Use an ordinary Markdown draft tab with a stable draft identity and native document-change events. Source tabs remain ordinary; writing moves into a separate tab and the anchor needs explicit presentation.
3. Keep native comment writing and retain text only after an explicit action. This weakens confirmed unfinished-text retention and is not an acceptable automatic fallback.
4. Replace the code surface with a custom editor or require proposed/internal APIs. A custom editor owns its HTML UI; the former changes ordinary editor behavior and the latter conflicts with the confirmed stable-public-API target. [Custom editor mechanism](https://code.visualstudio.com/api/extension-guides/custom-editors), [proposed API policy](https://code.visualstudio.com/api/advanced-topics/using-proposed-api).

## Bounded host experiment and remaining unknowns

One disposable extension, a tiny local Git fixture and mock records; no real AI, GitHub writes or repository switching. First run on 1.142.0; repeat on the eventually selected minimum version and Windows/macOS/Linux. Record exact host/Node/shell versions and visible outcomes.

1. Open immutable original/modified URIs in native split/unified diffs plus an editable working file. Verify old/new/file anchors, renamed/deleted files, same-line public/private threads, Comments Panel, collapse, source reveal and return focus. Test file-thread creation sequence.
2. Type whitespace, multiline Markdown, Unicode/IME composition and an unfinished suggested-change block into native input. Navigate, collapse, close, reload and exit. Record whether any stable observable event supplies exact input; host retention alone does not establish an autosave contract. Do not implement an unsupported internal-model workaround.
3. Only after owner approval, exercise the selected owned composer with per-edit revisions and durable acknowledgments; simulate slow/failing saves, webview disposal, immediate navigation, reload and process interruption. Specify exactly which acknowledged text survives; no experiment can establish zero-loss power-failure behavior without a defined persistence model.
4. Move/hide/recreate navigation and companion, narrow the window, change themes/high contrast and zoom; exercise keyboard-only and screen-reader flows. Confirm Context / Chat remains available and editor focus is recoverable. Native accessibility includes comment Accessible View and diff navigation, but owned UI needs its own checks. [Accessibility](https://code.visualstudio.com/docs/configure/accessibility/accessibility).
5. Run short/failing/long checks in a dedicated terminal with shell integration enabled/disabled. Observe immediate output capture, unknown exits, Ctrl+C/terminate/dispose and child-process survival on each OS; preserve output and prevent occupied user-terminal reuse.

Remaining research boundaries: no host behavior, runtime measurement, minimum-version compilation, packaged native dependencies, keyring failure path, remote execution/credential boundary or crash-durable writer has been tested. Exact native focus/old-side/file anchors and accepted composer treatment remain gated by those checks and the owner decision. This note proves neither Git/GitHub lifecycle safety nor provider compatibility.
