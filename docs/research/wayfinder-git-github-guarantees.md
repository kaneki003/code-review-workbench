# Git lifecycle and GitHub API guarantees

Research date: 15 October 2026. Supports [Establish Git lifecycle and GitHub API guarantees](https://github.com/kaneki003/code-review-workbench/issues/3). Fact-finding only: this note selects no architecture and performed no checkout, review, comment, merge, or queue mutation in a user repository.

The approved PRD and current design contract remain authoritative. Entry opens a local target repository and PR branch while preserving unfinished work; unsafe preservation permits local reading without switching. Exit restores the prior workspace, branch, and work. Ordinary editing remains available. Local drafts remain distinct from GitHub pending reviews. The owner confirmed stable desktop VS Code across Windows/macOS/Linux and an initial working local review loop; publication follows later.

## Preservation mechanisms and boundaries

| Mechanism | Documented behavior | Consequence to investigate; not a strategy selection |
| --- | --- | --- |
| Existing-worktree switch | A clean tree is not mandatory, but Git aborts when switching would lose changes. `--discard-changes` replaces index/worktree state; `--merge` is a different operation, not preservation. [Git switch](https://git-scm.com/docs/git-switch) | A successful switch alone does not prove prior edits were isolated. Never turn refusal into an automatic force/reset. Inventory before and verify after each transition. |
| Stash and restoration | A stash records working-directory/index changes. `-u` includes untracked files; `-a` also includes ignored files and cleans them. `apply --index` attempts index restoration but can conflict; `apply` retains the stash, while successful `pop` removes it. Stash ordinals move as entries are added. [Git stash](https://git-scm.com/docs/git-stash) | A stash is not a universal workspace backup. Record its object identity, original HEAD/ref, and ownership; verify restored staged/unstaged/untracked content before releasing recovery data. Unsaved editor buffers require host handling. |
| Linked review worktree | Linked worktrees have separate HEAD/index/worktree files, but share ordinary refs and normally repository configuration. Git refuses a branch already checked out elsewhere unless forced. Clean removal refuses modified/untracked files; force overrides it. Submodule support is incomplete; worktree move excludes submodules. Stable machine-readable listing supports `--porcelain -z`; lock/repair protect administration in specified cases. [Git worktree](https://git-scm.com/docs/git-worktree) | The original directory can stay untouched, but refs/configuration are not independent. A lock is not an application-wide writer mutex. Exiting must retain review edits and never force-remove a dirty review worktree. Whether a separately named local review branch meets the product's PR-branch wording is an owner decision. |
| Separate clone | Cloning creates a new directory. Local clones can hardlink objects; `--shared`/alternates introduce dependency on the source repository, and local cloning can race with source changes. [Git clone](https://git-scm.com/docs/git-clone) | Independence depends on clone options. Extra storage, credentials, dependencies, and workspace restoration still need treatment. Clone failure cannot become a successful remote-only review. |
| No-switch reading | Git can compare commits independently of checkout, including `A...B`, which compares a merge base with B. [Git diff](https://git-scm.com/docs/git-diff) | This can preserve the approved local reading fallback. The visible source revision and current editable worktree must remain distinguishable; ordinary file tabs must not masquerade as the PR head. |

Preflight can use `git status --porcelain=v2 -z`, which distinguishes index/worktree, unmerged and untracked records, including branch metadata; submodule status has additional meaning. [Git status](https://git-scm.com/docs/git-status) Inference: unfinished merge/rebase/cherry-pick, unmerged index entries, externally changing files, and uncertain submodule state should be treated as preservation hazards, not assumed stashable.

Cross-platform limits matter: `core.ignoreCase`, `core.protectHFS`, `core.protectNTFS`, `core.symlinks`, and line-ending/filter configuration alter checkout behavior. [Git config](https://git-scm.com/docs/git-config) A submodule is a separate repository with its own working state. [Git submodules](https://git-scm.com/docs/gitsubmodules) Missing Git LFS can yield pointer files instead of object contents, and GitHub may show only pointers in a PR. [GitHub LFS collaboration](https://docs.github.com/en/repositories/working-with-files/managing-large-files/collaboration-with-git-large-file-storage)

**Derived recovery obligations:** persist a transition journal before any source mutation or window handoff; record previous workspace URI(s), repository/common-directory identity, symbolic ref or detached HEAD OID, owned preservation objects/worktree/ref, and completed phase. Re-read actual Git/filesystem state after restart. Do not replay destructive commands from a journal. Another window, Git UI, or terminal can change state between checks: application coordination must detect stale ownership and retain recovery artifacts. Restoring the original workspace must not discard edits made during review.

## Revision accuracy, forks, and force-pushes

| Evidence | Fact and limit |
| --- | --- |
| PR ref | GitHub documents fetching `pull/NUMBER/head` into a local branch, including an inactive PR. Its `refs/pull/` namespace is read-only. [Local PR checkout](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally) Treat this as source acquisition, not permission to push to the author's fork. |
| PR comparison | GitHub displays a three-dot comparison from merge-base to head. [GitHub branch comparisons](https://docs.github.com/en/pull-requests/reference/branches#comparing-branches-in-pull-requests) Pre-merge `merge_commit_sha` identifies a test merge, not the PR head. [PR metadata](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request) |
| Stable comparison | Git's merge-base computation may yield multiple best common ancestors. Shallow history may need deepening; fetch updates refs according to its refspec and forced-update rules. [Git merge-base](https://git-scm.com/docs/git-merge-base), [Git fetch](https://git-scm.com/docs/git-fetch) |
| Metadata completeness | PR file listing caps at 3,000; PR commit listing caps at 250. [REST PR API](https://docs.github.com/en/rest/pulls/pulls) Local object evidence must not be labeled complete solely because an API page ended. |

**Derived anchor invariant:** capture repository/PR identity, inspected head OID, comparison base OID/merge-base, path, side, range, and original blob/context. Store fork repository identity separately from the base repository and local remote name. Do not use a branch name as immutable evidence. On Sync, keep the old anchor and record any proposed mapping separately; renamed files, force-pushes, deleted lines, missing objects, and ambiguous mappings require explicit outdated/unresolved status. An old approval/check/AI observation is not evidence about a new head. Fetching a newer ref must not silently move a dirty worktree or local user branch.

## GitHub.com user authentication and access

| Choice | Documented capability and constraint |
| --- | --- |
| VS Code account session | Stable `authentication.getSession('github', scopes, options)` obtains a consented session and supports account selection; session changes are observable. Accounts alone do not grant extension access. [VS Code authentication API](https://code.visualstudio.com/api/references/vscode-api#authentication) |
| OAuth app | Authorization-code and device flows are supported; device flow must be enabled and needs no client secret. Current GitHub.com supports optional expiring OAuth tokens and rotation. Revalidate identity after sign-in. [OAuth authorization](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) OAuth `repo` is broad read/write private-repository access, not a read-only private-PR scope; granted scopes can differ from requested ones. [OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) |
| GitHub App user token | Access is the intersection of user and app access; authorization and installation are distinct. Actions are attributed to the user with app attribution. [App authorization](https://docs.github.com/en/apps/using-github-apps/authorizing-github-apps) Expiring user tokens last eight hours; refresh tokens six months; rotation invalidates the previous pair. [Token refresh](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens) Native clients must not ship an app private key or use installation tokens for user-driven actions. [App best practices](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app) |
| User-supplied PAT | Fine-grained PATs select one resource owner/repositories/permissions and may require organization approval. Documented gaps include outside-collaborator and public contribution scenarios; classic PATs are broader. Expiry, revocation, organization policy, or lost membership can remove access. [PAT documentation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens) |
| SSO/private access | Classic PATs require SSO authorization; fine-grained PAT authorization occurs at creation. Unauthorized organization access can return 403/404 or partial multi-organization results with `X-GitHub-SSO`. [REST authentication](https://docs.github.com/en/rest/authentication/authenticating-to-the-rest-api) Git transport credentials remain a separate concern from the API token. [GitHub authentication](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github) |

The built-in Git extension exposes repository state and Git operations, including worktree types, but its exported extension API is not the stable `vscode` namespace contract. Pin and inspect its version if used. [First-party Git extension declarations](https://github.com/microsoft/vscode/blob/main/extensions/git/src/api/git.d.ts) This note does not establish that an API session automatically configures all Git subprocess credentials.

## Relevant PRs, discussion, and publication capabilities

Relevance can be assembled per repository from `author:`, `assignee:`, `mentions:`, `review-requested:`, and `reviewed-by:`; `involves:` is a different union and omits review request semantics. Team requests need explicit coverage. Requests disappear after review, while reviewed-by preserves history. [Search qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests) Manually added and locally retained reviews require the product's own index.

Search caps at 1,000 results; `incomplete_results`, inaccessible repositories, and timeout handling prevent assuming complete absence. Authenticated non-code search normally allows 30 requests/minute. [Search REST API](https://docs.github.com/en/rest/search/search) Follow REST pagination links and every GraphQL connection's cursor, including nested thread comments; GraphQL page sizes are 1–100. [REST pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api), [GraphQL pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api)

| User action/data | API and constraint |
| --- | --- |
| General PR discussion | Issue comment list/create/update/delete endpoints; PR-wide comments are not source threads. Fine-grained create accepts Issues **or** Pull requests write. [Issue comments REST](https://docs.github.com/en/rest/issues/comments) |
| Immediate inline/file comment; reply; edit/delete | Review-comments REST supports commit/path, line/side and optional range, or `subject_type:file`; reply targets a comment ID and ignores other anchor fields. Fine-grained writes require Pull requests write. Old commit attribution may make comments outdated. [Review comments REST](https://docs.github.com/en/rest/pulls/comments) |
| Review bodies; pending review; submit | Reviews REST lists reviews and review comments, creates a pending review when `event` is omitted, and submits by review ID. Creation accepts `commit_id`; submission accepts body/event. Write requires Pull requests write. Only pending reviews can be deleted; a submitted review is not deletable. [Reviews REST](https://docs.github.com/en/rest/pulls/reviews) |
| Threads, resolution, pending additions | GraphQL exposes review threads, original/current line fields, outdated/resolved flags, reply/resolve/unresolve viewer capabilities, and resolve/unresolve mutations. `addPullRequestReviewThread` adds to a pending review; `addPullRequestReviewThreadReply` handles replies. Prefer current line/range thread inputs over deprecated diff-position mutations. [GraphQL PR schema](https://docs.github.com/en/graphql/reference/pulls) |
| Suggested changes | GitHub supports suggestion blocks on selected lines/ranges; publication is a review comment, not application of that change. [Commenting guide](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/commenting-on-a-pull-request) |
| Own pending state | Pending line comments are visible only to their author until submission. Authors cannot approve their own PRs; request-changes blocking depends on rules and reviewer authority. [Reviewing guide](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request) |

**Derived completeness contract:** hydrate issue discussion, review summaries, source threads and all replies, plus the authenticated reviewer's pending review. Preserve server IDs and author/capability fields. Test own-pending visibility with the chosen token and pagination; do not assume another reviewer's private pending content is available. Local text is not remotely pending until GitHub confirms it. Resolve/reopen concerns a thread, not the review decision or PR state. Permission hints improve UI, but the server can still reject a stale action.

Discussion refresh can be independent of source checkout because its APIs are independent (implementation inference). Track separate freshness/completeness cursors. Conditional requests, serial writes, backoff, and `Retry-After` reduce API load; rate-limit errors can be 403 or 429. [REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) Standard authenticated REST budgets are normally 5,000/hour, with secondary constraints and token-dependent exceptions. [REST limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

## Head guards and merge outcomes

| Operation | Actual server guard or limitation |
| --- | --- |
| Create Comment/Approve/Request changes review | REST `commit_id` / GraphQL `commitOID` attribute the reviewed commit. Neither creation contract documents an atomic expected-current-head comparison. |
| Submit an existing pending review | REST and GraphQL submit inputs provide event/body/review identity, **no expected-head field**. Refresh-before-send remains a client-side race window. |
| Immediate source comment | `commit_id` anchors source; it is not an expected-current-head compare-and-swap. |
| Direct merge | REST `PUT …/pulls/{number}/merge`: `sha` guard, mismatch 409; Contents write; excludes queue/stacked merges. |
| GraphQL direct merge / enqueue | `mergePullRequest.expectedHeadOid` checks the head; `enqueuePullRequest.expectedHeadOid` supplies expected head. These are separate operations. |

Sources for these endpoint comparisons: [Reviews REST](https://docs.github.com/en/rest/pulls/reviews), [Review comments REST](https://docs.github.com/en/rest/pulls/comments), [GraphQL inputs](https://docs.github.com/en/graphql/reference/pulls#input-objects), [Direct merge REST](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request). The lack of a documented expected-head input is a contract observation, not proof of undocumented server behavior. Always retain the inspected commit on the receipt; do not describe a raced approval as approval of an unseen newer head.

Current GitHub.com documents asynchronous merge using `X-GitHub-Api-Version: 2026-03-10` in examples. Verify the implementation's pinned-version compatibility. [Asynchronous merge](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously)

| Endpoint | Receipt semantics |
| --- | --- |
| `PUT /repos/{owner}/{repo}/pulls/{number}/merge-async` | Contents write; `sha` pins head, otherwise request-time head. `direct_merge` / `merge_queue` / `default`; 202 UUID; existing pending request: 409 UUID/options. |
| `GET /repos/{owner}/{repo}/pulls/{number}/merge-async/{uuid}` | Contents write; pending / merged / enqueued / failed. Receipt expires 24 hours after latest update (404). Enqueued is final here, distinct from merged. [Result endpoint](https://docs.github.com/en/rest/pulls/pulls#get-the-result-of-an-asynchronous-merge) |

An accepted asynchronous merge request is not an eligibility certificate: rules run later. For queue behavior, GitHub can remove an entry when checks/rules fail; queue availability depends on repository/plan. [Merge queue guide](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request-with-a-merge-queue) Inference: show repository-enabled methods, permission/rules state and unknown eligibility honestly; do not infer final merge from a successful enqueue, auto-merge enablement, HTTP 202, or expired receipt. Re-fetch PR merged state and merge commit for confirmation. `mergeable:UNKNOWN` is a documented calculation state. [GraphQL mergeability](https://docs.github.com/en/graphql/reference/pulls#mergeablestate)

## Interrupted publication and duplicate prevention

The inspected comment/review contracts do not document a general idempotency-key facility. GraphQL `clientMutationId` is returned as a client identifier; it does **not** document duplicate suppression. [GraphQL mutations](https://docs.github.com/en/graphql/reference/pulls) The asynchronous merge UUID is an operation-specific receipt, not a general publication guarantee.

**Derived publication protocol:** durably record an intent and exact selected body/destination/actor/anchor/head before sending. Persist each returned object/review ID and URL immediately. An interrupted response produces **uncertain delivery**. Reconcile known IDs first; otherwise fully paginate the relevant author's review/comment/thread collections and compare exact body, anchor, reviewed commit and timing. Matching text alone is not unique: users can intentionally repeat comments, publish elsewhere, edit, or delete them. One empty page, failed read, account switch, or partial refresh never proves an operation was unsent.

| Interrupted action | Safe inference / unresolved risk |
| --- | --- |
| Create immediate comment or reply | Without a receipt or unambiguous server object, automatic retry can duplicate. Preserve uncertainty and offer explicit recovery after reconciliation. |
| Create pending review / add pending thread | Re-fetch the current user's pending review and its comments before attempting creation again. A pending review may pre-exist in another client; ownership is not implied by discovering it. |
| Submit known pending review | Re-read its ID/state, commit and children. Preview the actual complete remote review. Excluding an existing pending comment requires an explicit remote edit/delete; local selection does not remove it. A submitted review is evidence; a missing ID or empty pending list alone is not. |
| Merge / queue | Inspect the operation-specific receipt when available, then current PR/queue state. A lost UUID or expired receipt retains uncertainty about the request even if current state can establish eventual outcome. |

## Required fixture experiments and owner decisions

No destructive fixtures or live publication experiments were run. Before claiming cross-platform restoration, use disposable repositories to test staged/unstaged overlap, untracked/ignored collisions, intent-to-add, unresolved index, detached/unborn HEAD, in-progress operations, review-time edits, branch ownership in another worktree, concurrent external Git changes, crash at each transition, case-only renames, unusual paths/newlines, symlinks, line-ending/filter failures, sparse/shallow repositories, dirty/nested submodules, and missing LFS objects. Unsaved tabs, multi-root workspaces, window reloads, and original-window closure need stable VS Code host experiments.

Publication fixtures later need private/fork/SSO/permission coverage; nested pagination; own pending review imported from another client; old-source/range/file anchor rejection; head push between preflight and review submission; delayed/lost responses before and after server acceptance; review edit/delete during reconciliation; merge method/rules changes; and queue removal/receipt expiry. Never use a real user's unfinished work as the fixture.

Owner decisions remain: whether linked worktrees/separate clones satisfy the approved checkout/restoration language; the recoverable policy for review-time ordinary edits; minimum Git/version/platform limits and truthful unsupported cases; whether broad built-in OAuth private access is acceptable versus an app installation flow; the presentation/reconciliation protocol for pending reviews created elsewhere; and the visible treatment of unavoidable head-race/uncertain-publication cases. Existing GitHub pending comments remain actual remote records included in a submitted review unless explicitly changed/deleted remotely. M1 can establish real-PR local entry, revision-accurate ordinary diff tabs, anchored local autosave/resume and verified safe exit before any publication is enabled.
