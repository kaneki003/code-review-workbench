# Private review state and recovery storage

Status: accepted storage direction and planning contract, 15 October 2026, confirmed through the owner's discussion rounds. The owner explicitly deferred the detailed local-to-later-PR linking workflow to implementation. This document selects the storage rules and records required implementation checks; no production storage, migration, deletion or recovery behavior has been implemented or tested.

Decision: [Choose durable private state and recovery storage](https://github.com/kaneki003/code-review-workbench/issues/8), within [Plan the Code Review Workbench technical design](https://github.com/kaneki003/code-review-workbench/issues/1).

Read the [product requirements](../product/PRD.md), [design precedence](README.md), [extension architecture](extension-architecture.md) and [Git/source lifecycle](git-source-lifecycle.md) together. The GitHub and AI decisions will supply their own endpoint/runtime details; this document must not invent those outcomes.

## Confirmed foundations

1. Use SQLite for authoritative on-device private review state. Group related writes in transactions rather than maintain a general-purpose transaction protocol across JSON review files.
2. Retain private review work until explicitly cleared. Recomputable caches can have separate cleanup rules; age alone must not delete conversation, decisions, attachments or unfinished feedback.
3. Keep one verified automatic local recovery backup, plus a temporary pre-migration backup. Clearing private review data also removes that content from app-managed backups.
4. Clearing removes private content while retaining only necessary, separately disclosed review recovery records until unfinished workspace transitions or uncertain deliveries are reconciled. Repository work, personal review profiles and GitHub records are outside PR-private-data deletion.
5. Use the selected VS Code runtime's built-in `node:sqlite` connection in a packaged Node worker. Node 24.21.0 labels it Stability 1.2, release candidate. The owner accepts that tradeoff, subject to actual minimum/current VS Code packaging and capability checks on Windows, macOS and Linux. A failed gate returns the driver choice for decision; it does not authorize a silent fallback to JSON or weaker persistence.
6. Save typing after about 300 ms of inactivity, with a maximum one-second interval during continuous typing. Show Saving/Saved/Failed; only a confirmed durable database commit acknowledges Saved. Close/Escape wait for the current input to save, retain the composer on failure and offer Retry. Discard explicitly deletes the draft and invalidates delayed saves. A crash can lose unacknowledged input.
7. Keep GitHub accounts' private reviews and personal review profiles separate. An account switch never changes a draft's actor or target, and does not bypass one-active-review ownership. Switching back restores the original account's work.
8. An unreadable database presents explicit recovery choices and backup age. Do not silently create an empty replacement or silently roll back to a backup. Disclose any retained damaged copy and reconcile actual repository/GitHub state before resuming interrupted operations.
9. Use a shared app-data folder for the current operating-system user, across supported local VS Code windows/installations. One window owns the active review; other windows explain where it is open. Takeover requires verified safe ownership transfer, not just an expired heartbeat.
10. Support deliberate association of a local investigation with a verified later GitHub PR. At the owner's request, defer the interaction, content-transfer/merge strategy and existing-PR-history conflict handling to implementation. No automatic conversion or history merging has been approved. Keep identifiers and original source references capable of supporting that later work.
11. Automatically migrate compatible stored data after making a verified backup. A migration failure rolls back; older extension versions refuse writes to an unsupported newer format.
12. Clear private data and Exit Review remain separate actions. Clear can leave the review active on the same code with empty private state. Invalidate old work so it cannot repopulate deleted content; retain only disclosed recovery protection as necessary.

## Storage location, driver and packaging

Use one application-owned root outside repositories and outside a particular VS Code workspace, profile or user-data directory:

| Platform | Default root |
| --- | --- |
| macOS | `~/Library/Application Support/CodeReviewWorkbench` |
| Windows | `%LOCALAPPDATA%\\CodeReviewWorkbench` |
| Linux | An absolute `$XDG_DATA_HOME/code-review-workbench`, otherwise `~/.local/share/code-review-workbench` |

Resolve this through a small host-only platform function, using the operating-system user's application-data location. Never derive it from repository content, the selected PR or a webview path. Reject relative/unsupported roots. Validate that the effective filesystem is local and supports the required locking/durability behavior; redirected/network storage does not become supported merely because its environment variable is set. An unsupported root stops review mutations and explains the limitation. Do not silently start a second store in another directory.

All copies first discover the canonical store through a small versioned registry at `<os.userInfo().homedir>/.code-review-workbench/store-location.json`, using the OS-provided home rather than an environment-overridden `HOME`/`USERPROFILE`. Serialize first registration/guard discovery at that fixed rendezvous; atomically register the chosen root and store ID once. Different `XDG_DATA_HOME`/`LOCALAPPDATA` values in later processes must not initialize another store: honor the validated registered root or fail with an explanation. Missing/malformed registry alongside existing storage is recovery, not permission to reset identity. The registry/rendezvous filesystem must also satisfy the local locking/durability gates. [Node's OS-provided user information](https://nodejs.org/download/release/v24.21.0/docs/api/os.html#osuserinfooptions).

Initial layout: `review.sqlite` with SQLite-managed WAL/SHM files; `backup/` for the verified recovery bundle; `migration/` for a temporary pre-upgrade bundle; `content/<owner-id>/<review-id>/` for immutable attachment/local-snapshot files; and `recovery/` for small versioned operation records, the current store incarnation, pending clear markers and ownership information. Register temporary and quarantined recovery copies so clearing and diagnostics can find them. Restrict the application directory to the current user through normal platform permissions. Logical GitHub account separation is not a claim that files are inaccessible to other programs running as that operating-system user.

The same operating-system user and same resolved root form the coordination boundary; another computer or OS login has independent state. Supported local VS Code copies must use this root and the same format/ownership protocol. Remote SSH, WSL, Dev Containers, Codespaces, tunnels, virtual workspaces and browser VS Code remain outside the accepted architecture. Check the environment before opening the store for review operations; do not relocate private records or interpret remote repository URIs as local paths. No cross-device sync or new session-management screen is introduced. Uninstalling VS Code/this extension is not an implemented private-data deletion mechanism.

Construct `node:sqlite` connections inside a packaged Node worker. Use short parameterized SQL statements and explicit numbered migrations; no ORM or additional database service is needed initially. Set and verify `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, `secure_delete=ON` and a bounded busy timeout. Keep transactions short and never hold one while awaiting Git, GitHub, AI, file extraction or user input. A busy/failed commit remains Saving/Failed, not Saved. Do not delete live WAL/SHM files manually.

Ship the worker as an explicit VSIX asset, keep Node built-ins external to its bundle and test loading it from the installed extension. The driver comes from the extension host, not the developer's separately installed Node. Preserve the architecture's pinned build toolchain; enabling this driver does not add a native add-on or install hook. Minimum/current VS Code and advertised OS/architecture combinations must exercise worker startup, transactions, backup, checkpoints and failure handling. Missing/changed driver capability blocks private-state-dependent operations with an explanation; it never creates an empty fallback database or sends unjournaled external operations. Ordinary editor use remains available.

## Identities, records and authority

Use stable opaque IDs for local records and Git objects; do not key records by display names, branch names or stash ordinals. GitHub identity uses host plus immutable GitHub user/repository IDs. A login name can change. Every private child record belongs to a review and its owner scope; validate both on reads/writes and use foreign keys/composite uniqueness to prevent cross-account references.

| Entity | Key and minimum stored meaning |
| --- | --- |
| Storage metadata | Format/schema version, migration history, last committed sequence and the database's current store incarnation. The canonical incarnation is also kept outside restorable snapshots. |
| Account and personal review profile | Account key `(host, user-id)`; display login, host-owned authentication reference and one profile's text/revision. No credential bytes. |
| Local owner scope | A stable on-device identity for local comparisons made before GitHub sign-in. Sign-in never silently transfers that content into an account. |
| Local repository | Registration ID, canonical worktree path, per-worktree/common Git-directory identity and replacement/move detection facts, following the Git contract. Separate clones remain separate local copies. |
| Review | Review UUID, owner scope, kind, repository registration, state/content generation and durable revision. A GitHub PR review additionally has a unique account-scoped `(host, base-repository-id, PR-number)` identity; local committed/uncommitted reviews retain their independent UUID and input selectors. |
| Later-PR association | Capacity to reference a local review UUID and verified PR identity without replacing original source identity. Exact transfer, canonical-record adoption and conflicts are deferred to implementation by the owner; do not infer automatic merging from this row. |
| Source generation and file source | Review/generation IDs; exact PR head, observed base tip, merge base and comparison method, or local comparison selectors/resolved commits/index/worktree snapshot. Per-file old/new path, blob/content ID, mode, staging facts and known rename mapping. Latest remote observation, checked-out HEAD and dirty files remain distinct facts. |
| Source anchor | Anchor UUID plus review, source generation/object, comparison side, path, content identity, range and optional server thread ID. PR-wide targets explicitly have no line anchor. Unavailable source retains its identity. |
| Navigation and checkpoints | Review-scoped revision; selected file/checkpoint, filter, order, membership, expansion, companion tab, focus and navigation-return anchor/concern. Store known identifiers, not executable commands. |
| Reviewed mark | Review, applicable file/comparison fingerprint and explicit human mark. Source reconciliation clears changed-file marks; AI activity does not set them. |
| Agent examination scope | Attempt/source generation plus actually inspected files/ranges and known limits. Separate from human progress and correctness claims. |
| Suggestion and dismissal | Stable suggestion ID, owner/review, category/impact/body, anchors, evidence and applicability; dismissal records its suggestion/evidence version and optional reason. Meaningful new evidence is a new explained state, not an unrelated reset. |
| Conversation and input | Stable turn ID, review, sequence, role, text, sources/attachments and editable-input revision. Same-PR decisions/observations retain attribution and freshness. |
| Attempt and partial response | New attempt ID for each retry, original user-turn ID, provider/configuration reference, inspected sources, outcome, partial text and last persisted output revision. Failed/stopped attempts are not rewritten as successful. |
| Tool activity and permission reference | Activity/attempt IDs, actual command/tool, source, captured output reference, completeness, timestamps and known process/outcome. Saved-grant scope/revocation references are owner-bound; the AI decision defines runtime-specific permissions. No tokens or secret-bearing command logs. |
| Attachment and non-Git snapshot content | Owner/review-scoped immutable file ID, relative app-owned path, digest, type, size, original-source metadata and extraction/completeness status. Do not rely on the original user file remaining present. Avoid shared cross-review content deduplication initially. |
| Local draft | Draft UUID, original target/anchor, body, edit revision, committed revision, row revision, review content generation and deletion state. Adoption/publication uses a separate operation; a draft is not a pending GitHub comment. |
| GitHub pending-review reference and discussion cache | Original account/PR/server IDs, last observed state, fetch time, completeness and freshness. GitHub owns the real pending/published records; cached counts are projections. |
| Delivery operation and receipt | Operation UUID, original account/review/target/action/source, exact immutable chosen payload and digest before dispatch, attempt/state, request/server identifiers when available and verified receipt. A payload edit creates a new operation/version. Endpoint-specific receipt evidence remains the GitHub decision's work. |
| Workspace transition/restoration journal | Operation UUID, owner token/generation, repository identities, phase, expected-before/observed-after facts, original workspace/editors/branch/commit, preservation manifest and exact stash/ref identities. Minimal independent recovery metadata is mirrored before external side effects. |
| Clear and recovery state | Review/content generation, clear operation ID/phase, protected recovery references and inventory of app-managed copies. Clear markers survive restoring an older snapshot until all known copies are sanitized. |

Locally authoritative: private conversation/decisions, attachments, drafts, dismissals, explicit human marks, review/navigation choices and operation intents/receipts recording what the extension knows. Git is authoritative for actual objects, HEAD, index, worktree and stash/ref existence. GitHub is authoritative for access, pending/published discussion and remote action outcomes. AI-provider state is not proof of a local save or a GitHub receipt.

Recompute generated Markdown overviews, view projections, counts, rendered Markdown, search indexes and accessible discussion caches. Retained AI summaries and observations still carry their original evidence; regenerating a cache never silently rewrites the conversation or makes old evidence current. Pin exact Git objects needed by saved anchors; keep non-commit snapshots through the private content store. Apply the accepted Git/source reconciliation rules transactionally when publishing a new inspected generation. A missing source stays unavailable rather than silently opening a current line.

Obtain GitHub credentials through host-side VS Code authentication sessions. Put extension-managed secrets in `ExtensionContext.secrets`; provider-owned login material remains in the provider's supported credential store as selected by the AI decision. Store only nonsecret references in review records. Never include tokens in content files, backups, webview messages, logs or publication payload metadata. SecretStorage uses platform facilities and does not justify a uniform keychain-strength promise for every Linux configuration. Switching accounts must revalidate the original actor rather than resolve an old operation through whichever session is currently signed in.

## Ordered saves, Close, Discard and restart

Use one ordered mutation queue in the owning storage worker. Each request carries its request ID, owner/account/review/target, store incarnation, ownership generation, review content generation and expected row/edit revision. Reject wrong scopes, deleted generations, stale writers and out-of-order edits before mutation. Duplicate request IDs have one durable result. Across workers/windows the ownership protocol below applies; an in-memory queue alone is insufficient.

Send typed changes to the host promptly, retaining unacknowledged text in the composer. Coalesce database writes in the host/worker after about 300 ms idle and schedule a write no later than one second after pending typing began. This is a scheduling target, not a guarantee of disk completion within one second. Keep the newest unsaved revision while a write is in flight; save it next. Persist text, original target, revisions and corresponding domain change in one transaction, then acknowledge the exact committed revision. A late acknowledgment for revision 4 cannot mark revision 5 Saved or replace its text. On failure, retain the current input and original target, show Failed and allow Retry.

Close/Escape flush the newest input and wait for its acknowledgment; a failed save keeps the composer open. Moving/hiding a native view cannot be assumed to provide a cancellable Close callback: received pending input remains host-owned and continues saving even if the webview disappears. Recreated views receive the current durable state and any live host-pending input. Unsent browser text, an abruptly killed host and failed disk writes remain explicit limits; never claim recovery of text that was not acknowledged. Webview state/retained DOM is not the durable source.

Discard advances the draft's deletion revision before considering the operation complete. Delayed typing writes/acknowledgments cannot recreate it; new feedback receives a new draft identity. Clear also increments the review content generation and rotates the relevant writer/view tokens. Source changes do not retarget drafts; account changes do not reassign them.

Persist user turns before starting their investigation. Save partial answer/tool-activity checkpoints on the same bounded cadence and persist final/stopped/failed outcomes before reporting them as saved. Retry adds an attempt under the original turn. A restarted host labels interrupted generation/execution as interrupted or outcome-unknown; it does not automatically resume a command, regenerate an answer or resend feedback. A closed/reopened view only restores a projection.

## One active review and operation ownership

All supported local windows/VS Code copies use the shared root. Before storage maintenance or starting review/Git/GitHub mutations, obtain an exclusive application-owned store guard with a unique owner token; then record the owner instance, process identity/start evidence, active review, heartbeat, store incarnation and fencing generation durably. Only that owner runs mutations, migrations and normal backup publication. Other windows show the active owner's location and cannot start a second active review or become a second writer. Different signed-in accounts do not bypass this rule or expose the owner's private review.

Initial guard creation must use an atomic filesystem primitive. Safe release/reclamation is a separate protocol: serialize claim/release/reclaim, compare exact owner tokens, and ensure a stale reclaimer cannot remove a newly acquired owner's guard. A bare `mkdir` plus pathname deletion is insufficient. A missing/incomplete owner record is uncertain ownership. No guard is removed merely because its timestamp expired. The concrete OS primitives and crash windows must pass the two-reclaimer/orphan-guard fixtures below before this protocol can be relied on.

Normal transfer uses an acknowledged handoff token between old/new owners, including folder-opening transitions. For takeover after interruption, establish that the previous owner cannot continue and account for every outstanding external child/process. Verify actual repository state and remote outcomes as applicable before advancing ownership. If those facts cannot be established, block conflicting operations and offer specific recovery instead of stealing ownership. Never infer that a dead host means a Git child stopped, or that a sent GitHub request was cancelled. Unknown states retain recovery protection.

Every mutation revalidates the canonical incarnation and current fencing generation in its transaction. Recheck ownership and expected repository facts immediately before each external action. Keep additional repository-operation ownership by canonical worktree/common Git-directory identity; acquire multiple repository scopes in a consistent order. Git's own locks are additional protection. This coordinates cooperating extension versions, not every external Git client; revalidate actual HEAD/index/files and stop on unexpected changes.

The independent versioned control/recovery records contain only ownership/incarnation, clear barriers and necessary operation facts. Write them through a validated durable file protocol: unique temporary file, flush, atomic publication and platform-appropriate directory durability before acknowledgment. SQLite and filesystem updates are not one transaction: persist external-operation intent in the recovery record and database before dispatch; if either write fails, do not dispatch. Persist observed outcome/receipt, then update the database projection. Any missing receipt or disagreement means reconcile actual state, never repeat by assumption. Do not mirror every keystroke into JSON.

The canonical store incarnation is never rolled backward with a backup. A restore rotates it and invalidates all old connections/messages before new work. Reclaimed guards and sidecar durability are required cross-platform implementation gates; inability to establish them disables unsafe transitions rather than weakening the contract.

## Backup, upgrades and corruption

Maintain one verified regular recovery bundle. Initially schedule a backup after at most five minutes of dirty saved state and on a clean owner release when practical. A backup failure is visible; it does not undo a successfully committed draft or invent a backup. Backups may be older than Saved data, so corruption recovery can lose newer acknowledged work and must show the backup timestamp/cutoff. Retention does not promise unlimited disk capacity or immunity from disk loss.

Use SQLite's supported backup mechanism and verify the completed snapshot's integrity, schema, store identity, committed sequence and referenced-content manifest. Derive those facts from the completed snapshot, not a timestamp/current-memory read at backup start. Bundle required immutable attachment/local-snapshot files; make a candidate current only after its references and digests verify. Serialize backup/clear/migration publication through the owner queue; a changed clear generation invalidates a candidate. Do not block typing for the entire duration of a large incremental copy. Never copy an arbitrary live DB file without its correct transactional state.

For an upgrade, under exclusive ownership: verify format compatibility and integrity, make a verified pre-migration bundle, run numbered schema/data migrations in a transaction and verify the result before accepting new writes. Record applied versions exactly once. Create/verify the new regular recovery bundle before removing the temporary pre-upgrade one. Failure rolls back and preserves recovery options; it does not silently restore old data across a later clear barrier. Older extension copies fail closed on newer formats/protocols and explain that they need updating. Do not attempt automatic schema downgrades.

If the main database is malformed/unreadable, stop state-dependent mutations and present the error, backup age and recovery choices. Under exclusive maintenance ownership, preserve a registered/disclosed damaged copy, restore a verified candidate only by explicit choice, honor outstanding clear barriers, rotate the store incarnation and reconstruct projections. Before continuing, reconcile Git/workspace journals and GitHub receipts. Every operation restored from a backup is reconciliation-only until its actual outcome is checked; never automatically reapply a stash or resend a comment because an older snapshot says pending. A restored backup's old ownership flags are not authority.

If backup/control/recovery data is also missing or corrupt, explain the lost/unknown facts and preserve Git work/recovery refs. Do not offer destructive automatic restoration or an empty replacement as if safe recovery succeeded. Ordinary editor/Git recovery can remain available. Diagnose only known metadata; do not write private bodies or credentials into diagnostic logs. An abandoned or ambiguous maintenance guard requires verified recovery, not another window's time-based cleanup.

## Clearing private data without resurrecting it

Clear and Exit Review stay separate. Clearing an active review keeps the same inspected code and a blank private projection; it never changes branches, applies/drops stashes, deletes source files or submits/discards a GitHub pending review. It removes the review's local conversation, decisions, attachments, source snapshots/caches, suggestions/dismissals, progress/navigation and draft text. Account/profile and GitHub records remain outside this deletion scope. Later discussion refresh may fetch real GitHub records again; that is not restored private history.

1. Acquire ownership and durably publish a content-free clear intent outside restorable snapshots. Identify the review/owner and next content generation. Fence old views, saves, backup candidates and AI attempts; stop work where possible, and retain uncertain external effects for reconciliation. Undispatched delivery intents must not be sent. A sent request cannot be recalled by deleting local state.
2. Identify the exact minimal recovery remainder and explain it before claiming completion: original owner/account/PR/repository references, operation kind/ID/phase, stash/ref identities, branch/workspace restoration facts, content/staging fingerprints and remote request/receipt identifiers or payload digest when needed. Keep no deleted chat, draft body, attachment or model conversation in that remainder. Git stash contents that protect prior work/review-time edits remain repository work, outside private-content clearing.
3. Delete private rows transactionally with secure deletion enabled; remove app-owned review content and release only proven-unneeded review source refs. Recovery-protecting refs/stashes survive. Purge or regenerate regular/pre-migration backups, failed backup candidates, temporary snapshots and registered damaged/quarantine copies containing the cleared content. An unreadable copy that cannot be sanitized must be removed as a whole when safe; if that fails, report cleanup incomplete and its location instead of claiming it is cleared.
4. Compact/scrub as required, complete SQLite checkpoint/truncation successfully and verify app-managed copies/manifests no longer expose the cleared content. A busy checkpoint or filesystem failure leaves clear pending with Retry. Never manually unlink a live WAL. A valid sanitized backup can be recreated afterward; during cleanup, an invalid old backup must not be offered for restoration.
5. Acknowledge Clear complete only after content cleanup verifies, explaining any minimal recovery remainder. Resume a blank projection/new provider context, not an old provider session that repopulates deleted local history. The AI decision must honor this generation barrier. Retire content-free clear markers only when no retained snapshot/candidate can resurrect the old generation and old writers are invalidated. On restart, finish pending clear before showing review history or restoring backups.

When recovery finishes, remove its remaining operation facts once no retained snapshot can cause an unsafe replay; otherwise enforce reconciliation-only restore. Never retain a full private body as a hidden recovery convenience. App-managed deletion is not a promise to erase external model/GitHub records, operating-system backups or physical storage remnants. Required recovery protection is visible, limited to its purpose and not a secret second review history.

## Accounts, local comparisons and later PR association

Key account data by immutable host/user ID. A sign-out/account change fences old requests and disables old-account external actions until that account is reauthenticated. Preserve unsaved input and reconcile already-started effects against their original actor. Returning to the original account restores its saved state. Starting another account's review still requires safe release/restoration of the active review; authentication events do not perform an implicit checkout or transfer private content.

Local committed/uncommitted comparisons keep their own review IDs, exact source generations and owner scope before any PR exists. Reserve association metadata for a deliberate verified PR destination. Validate repository identity/access and accurate source correspondence; branch-name equality alone is insufficient. Local-only work has no invented publication destination, and association never grants permission to publish, changes the actor or silently retargets an old draft.

The owner explicitly requested that the detailed local-to-later-PR linking interaction and treatment of two existing histories be worked out during implementation. That follow-up must decide canonical-record adoption/transfer, conflicts, duplicates and anchor validation with concrete examples before enabling linking. This document does not select the earlier proposed conversion/history behavior. Preserve enough identities/provenance for a future migration; do not advertise linking as implemented or fully specified. This is an intentional planning exception, not an unresolved choice to answer on the owner's behalf.

## Initial bounds and failure behavior

Starting implementation parameters, to be verified with fixtures rather than treated as measured performance: one draft/message input up to 1 MiB UTF-8; one imported text/code/Markdown/PDF attachment up to 10 MiB raw; up to 1 MiB captured text per tool activity; and 64 KiB transport chunks with explicit complete-payload assembly before committing a large edit. Label captured/extracted output that is partial. Provider context/extraction limits remain the AI decision's responsibility and cannot silently truncate the saved original attachment or input.

Reject oversize imports before accepting them. If an input cannot be saved, retain it visibly with a specific failure and copy/recovery path; never acknowledge a truncated value as Saved. Do not accumulate unbounded queued tool output or webview payloads. Warn about growing local storage and low disk space, offer explicit review clearing and evict only recomputable unneeded caches. No automatic expiry of private work is introduced. Disk/permission/space errors preserve acknowledged state and recovery refs, stop unsafe external actions and explain what remains unsaved. Limits may be adjusted through implementation evidence without deleting existing content or changing these behavioral rules.

6. 10. Clear inactive and active reviews with pending GitHub reviews, published comments, uncertain sends, unfinished restoration and separate review-time stashes. 11. Crash/failure at every clear phase; busy checkpoints; stale WAL; regular/pre-migration/temporary/damaged copies and stale backup candidates. Search app-managed logical/scrubbed stores for fixture content; verify restart completes or reports pending cleanup rather than restoring it.
12. Corrupt main DB, corrupt/absent backup, damaged control records and unsafe restoration preconditions. Assert explicit recovery choices, accurate data-loss limits and no automatic replay/destructive repair. Include content removal from a disclosed damaged copy.
13. PR force-push, source rename/deletion/base-only changes, local snapshots, original anchors, account rename/switch and later-association metadata. Assert identity/ownership/freshness persist without silently moving drafts. The detailed linking workflow gets its own implementation scenarios before it is enabled.

The Git/source contract's broader preservation fixtures remain binding. The GitHub decision must fit endpoint-specific receipts and account access into this storage model; the AI decision must fit attempts, cancellation, permissions and clear-generation handling into it. The overall technical design still awaits those decisions and final acceptance.

## Established external facts

- SQLite transactions provide grouped all-or-nothing updates; the selected sync/journal settings and filesystem behavior remain part of the implementation's durability boundary. Use the stronger durable commit configuration, not a setting that knowingly acknowledges commits vulnerable to ordinary power loss. [Transactions](https://www.sqlite.org/transactional.html), [synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous).
- `DatabaseSync` is synchronous. Construct and use connections inside the worker; wrapping a synchronous call in a Promise does not move it off the extension host. Node's `sqlite.backup()` is asynchronous and uses SQLite's backup mechanism. [Node 24.21.0 SQLite](https://github.com/nodejs/node/blob/v24.21.0/doc/api/sqlite.md), [workers](https://github.com/nodejs/node/blob/v24.21.0/doc/api/worker_threads.md).
- Electron 43.7.7, pinned by the accepted VS Code runtime baseline, embeds Node 24.21.0. Actual packaged worker availability still needs a smoke test. [Electron release](https://releases.electronjs.org/release/v43.7.7).
- VS Code provides extension file storage and a separate encrypted SecretStorage API. File storage does not itself supply a public cross-window ownership protocol. Independent user-data directories are isolated, so extension global storage must not be treated as a machine-wide lock. [Storage APIs](https://code.visualstudio.com/api/extension-capabilities/common-capabilities#data-storage), [isolated user-data directories](https://code.visualstudio.com/docs/configure/command-line#advanced-cli-options).
- Live backups must use a supported snapshot mechanism, not an arbitrary copy of a changing database file. Removing live records alone does not sanitize older backups. `secure_delete`, checkpoint completion and compact sanitized snapshots need an explicit deletion protocol. [Backup](https://www.sqlite.org/backup.html), [pragmas](https://www.sqlite.org/pragma.html), [VACUUM](https://www.sqlite.org/lang_vacuum.html).
