# Git preservation and source synchronization

Status: accepted contract, 15 October 2026. The owner selected the behavior below through the wayfinder discussion and confirmed the final shared understanding. This document plans future implementation; it does not establish tested preservation, platform support or recovery guarantees.

Decision: [Choose Git preservation and source synchronization contracts](https://github.com/kaneki003/code-review-workbench/issues/7), within [Plan the Code Review Workbench technical design](https://github.com/kaneki003/code-review-workbench/issues/1).

Read the [PRD](../product/PRD.md), [design precedence](README.md), [interaction contract](figma-interaction-contract.md) and [accepted architecture decision](https://github.com/kaneki003/code-review-workbench/issues/6#issuecomment-6191239943) for the governing baseline. The [Git/GitHub research](https://github.com/kaneki003/code-review-workbench/blob/2e9adb7c81f6fff2df0850b71f7c701b9ae80fa8/docs/research/wayfinder-git-github-guarantees.md) establishes external capabilities and limits. This contract selects their application; the storage, GitHub and AI decisions still choose their own implementations.

## In plain language

Use the existing local repository folder. Save unfinished files, put unfinished Git changes in a stash, open the PR branch, then restore the previous workspace, branch and work on Exit Review. A local repository is required; a missing repository starts the clone flow. Do not create a linked worktree or a second clone when a suitable local copy already exists.

Reviewing requires no source editing. If ordinary editor use or a command does change files, Exit Review offers **Stash these edits and exit** or **Stay in review**. Sync similarly offers **Stash edits and Sync** or **Keep this version**. Those edits remain in a clearly named ordinary Git stash; never automatically mix them into the original work or the newer PR source. Explain where the stash was saved and how to recover it through ordinary Git tools. This is recovery for normal editor use, not a dedicated PR source-editing or per-PR edit-retention feature.

A known failed entry restores the original work automatically when the actual state proves that safe. An interrupted transition is checked when its affected local repository is reopened. Only that repository triggers the recovery choice; opening an unrelated project does not show it. A normal, completed review resumes automatically.

If checking for newer PR source fails, allow reading the retained local source and saved notes. Show **Couldn't check for updates · Showing previously downloaded code**, the actual inspected version and Retry. Do not claim the source is current. Approval, Request changes and Merge require a successful current-source check through the GitHub contract; source-accurate comments on older code remain a separate permitted path.

## Identities and source records

Names and local remote aliases are display/configuration values, not immutable identities. Use opaque object IDs rather than assuming a fixed hash length.

| Record | Identity and meaning |
| --- | --- |
| Local repository | A stable local registration plus canonical worktree path, per-worktree Git directory and common Git directory. Detect a moved/replaced directory before reusing a record. Separate clones of the same remote are distinct local copies. |
| GitHub PR review | GitHub.com host, base repository ID and PR number. Keep the head/fork repository ID, head ref, account/access context and selected local repository separately. An account change never silently changes a draft or publication actor. |
| Local committed review | Local repository, review ID, original input selectors (fixed commit versus moving branch ref), two resolved exact commit IDs and comparison kind. Resolve branch names when opening or deliberately syncing; a fixed-commit selector remains pinned. Ordinary comparison reads do not change checkout. |
| Local uncommitted review | Local repository, review ID and immutable local snapshot generation, including starting HEAD (or an explicit empty base), captured index and saved working-file contents, nonignored new files and staging metadata. A modified editor buffer is distinct from saved file content. |
| PR source generation | Exact inspected PR head, observed base tip, actual merge base and comparison method. Store the latest successfully observed remote head separately, with observation time and freshness state. Checked-out HEAD and dirty local files are also separate facts. |
| Source anchor | Review/repository, source generation or exact object, old/new side, path, blob/content identity and range. Retain original context and known rename mapping. A thread reply also retains its server thread identity; PR-wide feedback has no invented line anchor. |
| Navigation return | Original source anchor, initiating concern, expanded record and focus target. Return reopens the cited source rather than silently opening its current counterpart. |

PR diffs compare the merge base with the exact inspected PR head, following GitHub's three-dot comparison. Keep both comparison inputs: a base-branch change can affect the diff even if the head does not change. Fetch enough history to establish the comparison. Multiple merge bases, incomplete history or inaccessible objects produce an explicit comparison limitation rather than an arbitrary complete-looking diff.

For local committed reviews, compare the two selected commit trees directly and label both inputs. For uncommitted reviews, capture the index and saved working tree separately without modifying the user's index or checking out another branch. The default combined comparison is HEAD to the captured saved working tree, including nonignored new files. Keep staged/unstaged distinctions available so a net working-tree diff does not erase the existence of staged changes. A selected staged or unstaged source comparison must identify its actual two inputs. Recheck HEAD, index and file fingerprints around capture; detected concurrent changes require bounded retry or an explicit capture failure rather than a mixed source generation. Later disk/editor changes are newer local content; refreshing the inspected snapshot is deliberate while the review is active. On resume, refresh moving branch selectors and uncommitted snapshots automatically, subject to capture safety and reconciliation; fixed-commit selectors never advance.

Local comparisons leave the checkout, index and working files in place: do not stash away the uncommitted source being reviewed. Unsaved editor text gets an explicit Save and capture path or a clearly labelled saved-source view; it is never silently attributed to disk or committed source. Exit restores review/editor focus and performs no Git rollback unless an actual entry transition was recorded. The PR-specific dirty-Exit/Sync stash choices below apply when a checkout must be left or updated, not merely because an uncommitted review contains changes.

Retain exact source objects needed by saved anchors and evidence under owned references; store non-commit snapshot content through the private source/storage boundary. A force-push is not permission to rewrite old anchors. Missing/deleted source stays identified as unavailable if it cannot be obtained. Private-data clearing must never remove user work or recovery protection merely because it also holds a source object.

## Preservation before a PR checkout

The local extension host coordinates Git through its source connection. Webviews do not execute shell commands or own preservation records. The storage decision must supply acknowledged durable journal writes and cross-window ownership; do not substitute webview state or an in-memory flag.

1. Resolve the PR and intended local repository, acquire the review/operation ownership described below, and read actual Git state. Record the prior workspace URI or folder list, affected repository and editor groups/tabs/positions, original branch ref and exact commit or detached HEAD, index/worktree inventory and a unique operation ID. A prior workspace in a different repository does not make that other repository a checkout target.
2. Preflight saveability, in-progress Git operations, nested repositories/submodules, filters, paths, permissions and branch ownership. Save relevant dirty editor documents through ordinary VS Code save behavior, including its normal save hooks. Re-inventory after saving. Cancelled/failed saves, an untitled document that cannot be safely retained, a save hook that keeps changing files, or uncertain buffer ownership prevents the transition. Never silently discard dirty buffers or assume Git contains them. Before a folder/window handoff, all affected unsaved documents must be saved or explicitly retained through a verified host recovery path; otherwise remain in the current workspace and offer safe reading.
3. Persist a preservation intent before invoking stash. Include pre-transition content/staging manifests, the previous stash-ref observation and a unique stash message marker. Run stash with nonignored untracked-file inclusion when needed. A clean repository needs no stash; an existing user stash must never be mistaken for a newly created one.
4. Identify the exact stash object, verify its relationship/content against the intended inventory, pin it under an owned recovery reference and durably record the result. Verify the intended tracked/index/untracked changes have been preserved and the worktree is safe to switch. A successful command exit alone is insufficient. Do not check out the PR while preservation is unverified.
5. Fetch the required PR/base source into owned refs, verify the exact fetched head against GitHub metadata, and compute the comparison. Fetching may precede stashing when it only obtains objects/owned refs; it must not update user branches or perform a pull. Do not put credentials in command logs or persistent remote URLs.
6. Check out an operation-specific, extension-owned local review branch at the exact PR head in the same folder. Install each new PR source generation on a fresh owned branch, failing rather than reusing an unexpected existing name. This represents the PR source without resetting an existing author/user branch or taking a branch already owned by another worktree. Use collision checks and `checkout --no-overwrite-ignore`; never force checkout, reset user branches or clean away files. Recheck actual HEAD, refs, index and worktree before and after the operation.
7. Persist the checked-out phase before opening a different target folder/workspace. The opening process locates the journal by repository identity, revalidates it and acknowledges ownership/activation. A successful request to open a folder is not proof that the new extension host activated. Establish the source generation and then show the review.

Ignored files, including existing `.env` and dependency folders, stay in place. Do not silently use `stash --all`, which would also remove ignored files from the working folder. An ignored-path collision stops switching and offers recovery/no-switch reading. Existing dependencies are not guaranteed to suit a PR's changed dependencies; report missing/incompatible prerequisites and use normal command permissions for any proposed setup. Do not automatically install or clean dependencies as a checkout side effect.

The preservation manifest distinguishes saved disk content from index content, file types/modes and nonignored new paths. Support for intent-to-add, sparse-index flags, filters, unusual paths and platform transformations requires fixtures; a representation the implementation cannot preserve faithfully gets the safe fallback. Superproject stash does not preserve unfinished work in a nested repository. Dirty submodules, unresolved index entries, unfinished merges/rebases/cherry-picks, unborn PR-checkout state and uncertain special repository state stop automatic switching. Detached original HEAD is supported by recording and restoring its exact commit. Clean submodule transitions also require validated handling; do not silently run recursive checkout/update/clean. Missing LFS data is labelled unavailable/pointer content and is not passed off as full source.

## Transitions and recovery

The journal records intent and the last verified result for each external step, not only a final success flag. Store expected-before/observed-after facts and recovery artifact identities. Each subsequent step first compares those facts with the repository's real state.

| State or event | Behavior |
| --- | --- |
| Preflight or save fails | Keep the current workspace/work intact; explain Retry and, when local source is available, no-switch reading. |
| Clone fails or is interrupted | No active remote-only review. Keep existing destinations untouched; identify the operation-owned partial clone, offer Retry or another destination, and reconcile before any reuse/cleanup. A usable completed clone is retained. |
| Preservation/fetch/checkout/open-folder fails after a transition started | Inspect actual state. Automatically restore prior branch/work only when preconditions prove it safe. Keep the original error visible. Partial/ambiguous changes enter recovery rather than pretending the old workspace is untouched. |
| Host/window stops between journal phases | On reopening a workspace containing the affected local repository, reconcile actual state and offer Continue opening the PR/Continue review or Restore my previous work as applicable. If neither is currently safe, explain the blocking fact and retain all artifacts. Unrelated repository startup shows no recovery prompt. |
| Active, source unchanged | Reopen saved review/navigation state; hiding/closing a view changes no Git state. Publication/merge does not exit. |
| Local review-time changes on Exit | Save normally, then offer Stash these edits and exit or Stay in review. A new owned preservation operation records these edits separately from prior work. |
| Exit restoration | Confirm owned checks have finished or stopped, preserve review-time changes, restore the original branch at its expected original commit (or exact detached commit), apply the exact prior-work stash with index restoration, and verify tracked/staged/unstaged/new content. Then restore the previous workspace/editor layout and acknowledge completion. |
| Restoration conflict, missing branch/stash, external branch movement or failed workspace open | Keep recovery context and artifacts; show a specific failure and Retry/return options. Never hard-reset a moved branch, apply the stash twice, discard conflict files or label Exit complete. If a recovery branch at the saved original commit is needed, offer explicit ordinary Git recovery instructions/action instead of silently renaming the user's destination. |
| Restoration is already complete after interruption | Verify it against the saved manifest and finish the receipt/cleanup. Do not apply the stash again. |

There is a crash window after `stash push` records/cleans changes but before the extension records the stash object. Recover by locating and verifying the unique operation-tagged object in the stash reflog, using the original HEAD, prior stash observation and inventory. Never assume the current `stash@{0}` belongs to this operation or blindly rerun stash. Ambiguity keeps the operation in recovery. Pin the identified object before proceeding. A user/external tool deleting recovery refs or manually changing/pruning Git data is an external interference case; do not promise recovery of objects that no longer exist.

Use `stash apply --index` so the backup survives restoration attempts. After any interrupted apply, compare actual files/index with the saved manifest before deciding whether it completed, partially applied or needs human recovery. Retain the backup until restoration and the durable completion receipt are verified. Delete only the exact proven-owned stash/ref afterward; stash ordinals move, so resolve and recheck ownership at cleanup. An ordinal recheck is not atomic against an external stash writer; if exact safe deletion cannot be established, retain the named stash rather than risking another entry. If cleanup is ambiguous, keep the artifact. A review-time stash explicitly chosen for later recovery remains a user-visible ordinary stash and is not automatically removed on Exit, Sync or private-data clearing.

No-switch reading uses revision-specific local source/diff documents and clearly identifies that the working folder remains on its previous checkout. Ordinary file/terminal paths still belong to that checkout. Workbench verification requiring PR files must not run there as if it were the PR. If preservation partially changed state, first expose/recover that transition; safe reading is not a claim that restoration has succeeded. Local reading cannot start without accessible local source.

## Source Sync and freshness

- Entry and normal resume attempt automatic latest-source Sync before making a current-source claim. An interrupted transition is recovered first. Resume with dirty PR files follows the explicit stash/keep choice below; this exceptional choice does not add routine session management.
- While a review is active, detect and announce new commits without changing its checkout or inspected source. Reviewer-triggered per-review or repository/list Sync authorizes an update. Discussion refresh is independent.
- Before changing active source, wait for workbench-owned verification to finish or be confirmed stopped. Stop requested is insufficient. Do not reuse or kill an occupied user terminal. Known unrelated repository-writing activity is also a reason to wait or pause; the extension cannot universally detect every external process.
- If PR files have local edits, save normally and offer Stash edits and Sync or Keep this version. Preserve edits, staging and nonignored new files in a separate named ordinary stash. Do not automatically replay them onto newer PR code. A failed stash leaves Sync paused.
- Fetch/compare into owned refs first, then recheck the expected local branch/head/index/files immediately before checkout. An unexpected manual branch switch, new commit, concurrent save or Git change pauses the operation for reconciliation. Never force the user's state back to the expected value.
- Verify fetched head/base inputs and re-read metadata around installation. Use expected-old-value ref updates wherever available. If the PR changes again, show the actual inspected generation and the newer/unknown state; use bounded retry on entry/resume, never an unbounded loop or a false current label. Client-side preflight cannot prevent a subsequent push on GitHub; the GitHub decision owns endpoint-specific action guards and receipt handling.
- A force-push is handled as a new source generation, not a normal fast-forward assumption. Keep pinned old objects/anchors. Deleted branches/forks, denied access, unavailable commits or failed fetches leave retained readable source labelled older/unknown and offer Retry. Do not change provider/repository/remote to evade access failures or silently compare unrelated source.
- Active Sync failure retains the prior inspected generation and saved review state. If checkout partially changed the worktree, reconcile/restore it or expose recovery; never show the old source label over a different checkout. Updating domain state and the Git worktree are separate durable phases, with restart reconciliation between them.

Repository/list Sync gathers per-PR results for the personally relevant PRs in the selected repository. It initiates the normal clone flow if local source is missing. For inactive PRs, obtain exact source and reconcile saved progress without sequentially checking out each PR or starting another active review. An active PR participates in the same explicit batch action, subject to running-check and dirty-edit gates. Continue independent inactive reads when the active update is deferred; report updated, unchanged, deferred, failed and freshness-unknown results separately. A batch operation must not switch focus or replace the active review. Cache updates do not claim that inactive code has been inspected by the person/agent.

## Reconcile review state without moving its meaning

Create a new source generation only from verified inputs, then durably publish the reconciled state. If this fails after checkout, recover using the journal rather than marking the previous generation current.

| Saved state | Reconciliation |
| --- | --- |
| Human Reviewed marks | Keep marks when the applicable file source/comparison remains unchanged; clear marks for changed files. Treat rename/mode/base-side changes according to the actual compared source, not only a filename or head blob. |
| Checkpoints and navigation | Keep the existing optional route and unaffected focus; update membership or introduce coverage for newly relevant areas. Deleted/moved targets have explicit unavailable/renamed states. Do not rebuild the route by default. |
| Local drafts and pending feedback anchors | Preserve text and original PR/file/side/range/revision/thread target. Offer deliberate retargeting only after the reviewer inspects it. An approximate line mapping never silently changes a draft. GitHub pending state remains server-owned. |
| Dismissals and suggestions | Preserve unaffected dismissals. Relevant code change or meaningful new evidence may justify resurfacing with an explanation; an unrelated update does not. Retained suggestions identify their inspected sources. |
| Evidence, answers and check output | Keep original content, source identity and real outcomes. Flag affected or uncertain dependencies as outdated/needs rechecking. Older approvals, checks or AI examination never certify new source. |
| Conversation and same-PR decisions | Preserve the history and its original attachments/sources. New-source answers are new evidence, not rewritten old messages. |
| Discussion refresh | Update accessible GitHub discussion, attribution, completeness and freshness independently; do not check out source, retarget private drafts or rewrite GitHub's outdated/resolved state locally. |

Ordinary source edits/buffers that differ from the inspected PR are labelled local changes. An explanation or command run against those bytes must identify that actual local snapshot/dirty state; do not attribute it to the clean PR head. Publication eligibility for such an anchor belongs to the GitHub contract.

## Ownership, compatibility and cleanup

One active review applies across the extension's windows. Use durable ownership of the active review plus serialized operations for affected worktrees/common Git directories; acquire multiple repository locks in a consistent order. Store an owner instance/operation and fencing generation so a stale process cannot continue committing state after ownership changes. A heartbeat/lease timeout alone does not prove another Git command stopped: inspect live ownership, child-process outcome and repository state before taking over. A second window can explain the existing owner and offer navigation; it cannot start a conflicting mutation.

This coordination covers cooperating extension instances, not arbitrary Git clients or every filesystem writer. Revalidate real branch/HEAD/index/worktree facts at command boundaries, preserve new unexpected content and stop on mismatch. Git's own index/ref locks are additional protection, not a replacement for the application protocol. Opening an unrelated repository leaves a pending recovery record alone; explicitly starting another review may explain the existing active ownership without showing an unrelated startup recovery prompt.

Use installed Git with required-capability probes. The initial compatibility target is Git 2.23 or newer, subject to validating the required stash, NUL-delimited status, protected checkout, worktree-ownership and expected-value ref operations on the minimum/current test matrix. This is an API compatibility target, not a recommendation to install an old Git release or a claim of tested support. Unsupported capabilities fail before mutation and offer an actionable Git update or safe local reading. Do not add a Git wrapper/framework simply for this plan; invoke bounded asynchronous operations through the existing source connection, with structured results and careful argument/path handling.

Clean up only proven-owned unused review refs/branches and transient clone artifacts after verified operation completion. Keep a branch if it gained user commits or unexpected ref movement. Never delete a usable clone simply because review ended, clear unrelated stashes, remove user files through cleanup, or remove recovery protection while a transition is incomplete. Cancelling a long Git operation records the actual outcome; a cancellation request does not establish that Git stopped before mutation. Inspect/reconcile after process exit or interruption.

The storage decision must implement journal/manifest durability, transactions, ownership/fencing and migration. Clearing private review data may remove notes/source caches under its policy, but must retain prior work, explicitly saved review-time stashes and unresolved recovery records. The GitHub decision must implement source freshness gates, anchor validation and endpoint-specific expected-head/receipt limits. The AI decision must attribute reads/checks to inspected source and respect running-check cancellation; it does not gain independent checkout/publication authority.

## Required acceptance fixtures

These are future implementation gates, not tests run by this planning session. Use disposable repositories and VS Code fixtures only; never a real user's unfinished work. Validate minimum/current Git and VS Code across Windows, macOS and Linux before advertising those support combinations.

1. Enter/exit from staged and unstaged changes on the same file, deleted/renamed files and nonignored new files; compare original disk/index/staging manifests after restoration. Include an originally clean tree and existing unrelated stashes.
2. Save failures/cancellation, save hooks, unsaved/untitled tabs, several editor groups, multi-root workspaces, another target repository, folder handoff, reload and original-window closure. Assert buffers are never silently lost and Exit is acknowledged only after real workspace restoration.
3. Crash/fault injection before/after each journal, stash, ref-pin, fetch, checkout, folder-open, source-state commit, apply, verification and cleanup boundary. In particular cover stash success before recording its object and apply success before recording restoration; assert no duplicate stash/apply and no premature backup deletion.
4. Review-time tracked/new changes on Exit and active/resume Sync, choosing stash versus stay/keep. Verify separate recoverable stashes, exact original-work restoration, retained staging and no automatic replay onto new PR source.
5. Stash/apply failures and collisions, changed/deleted original branch, original detached HEAD, unborn state, in-progress operations, unmerged index and external changes between preflight and command. Conflicted/ambiguous cases retain all artifacts and expose recovery.
6. Ignored-path collisions, retained `.env`/dependencies, unusual and newline paths, symlinks, case-only renames, executable bits, line endings/filters, sparse and shallow history, intent-to-add/index flags, dirty/nested submodules and missing LFS objects. Validate each supported case or its truthful no-switch/incomplete-source fallback.
7. Fork/private PR fetch, head/base movement before/during/after fetch/checkout, force-push, deleted branch/source, inaccessible historical objects and multiple merge bases. Verify exact source labels, retained old anchors and no user-branch reset.
8. New active commits do not change checkout until explicit Sync. Entry/resume attempt automatic Sync; unreachable GitHub retains labelled old code/notes with Retry. Older current-head-dependent actions remain gated; accurate old-source reading/comment paths remain distinct.
9. Wait/Stop with a real owned check, uncertain child termination, unrelated occupied terminals, two extension windows and stale-owner takeover. Assert no checkout before confirmed check stop/completion and no conflicting review writer.
10. Mixed-result repository/list Sync, missing-repository clone and active update deferred by checks/edits. Assert inactive PRs update without checkout/focus changes, one active review, independent discussion refresh and truthful per-PR results.
11. Changed versus unchanged file Reviewed marks, base-only changes, renames/deletions, original draft/reply targets, related-source return, dismissals, route adjustment and uncertain dependency evidence. Retention must not silently retarget or certify a newer source.
12. Cleanup after success/failure/private-data clearing, user-created review commits, shifted stash ordinals and missing/tampered recovery artifacts. Assert only proven-owned unused artifacts are removed and all known uncertainty is reported.

No new production implementation, real checkout/restoration or GitHub publication is authorized by this planning artifact. The agreed implementation milestones must demonstrate these behaviors with fixtures before relying on the preservation path in user repositories.
